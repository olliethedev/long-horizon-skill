# Ask the owner during ongoing work

During setup, agree on an authorized destination for actionable requests, how the owner replies, and how a future agent session finds the answer and resumes affected work. A report page or desktop notification may deliver a request without providing a reply channel. A supported fallback is for the owner to open a new session in the project and refer to the pending request.

When input is needed, save a durable request in the existing action history and link it from the current handoff. Include a stable identity, why input is needed, the exact decision or owner action, affected work, relevant alternatives or costs, and what permits resumption. Keep its status visible until resolved; avoid creating another request for the same unresolved issue.

Deliver a concise notice through the agreed channel and retain its receipt. Delivery acceptance is not proof the owner read or answered it. Preserve uncertain delivery and reconcile it before retrying. If delivery fails, leave the request and failure visible in the handoff and any available authorized reporting surface; do not invent a new contact channel.

Hold work dependent on the missing decision or prerequisite. Continue independent useful work within standing authority, preserving the pending request across scheduled runs. If no useful work remains, disable future runs for the responsibility and verify the pause. Do not schedule restoration polling or treat the blocked objective as impossible solely because owner input is needed.

When the owner responds, read the request and current instructions, record the answer, and verify the required access or prerequisite. Owner-paused work resumes only on explicit owner instruction, even if access now works. Confirm the affected scope and actual scheduler state when resuming; an unaffected active responsibility does not need reactivation. Preserve the original request and resolution for later sessions.
