# Setup interview

Use this process for a new responsibility. For established work, carry forward the current brief and standing authority; a fresh session or skill update does not require onboarding again.

## Discover and review tools

Inspect the request, project instructions, existing responsibilities, and relevant configuration. Derive the capabilities needed for this responsibility: evidence collection, acting on the product, checking outcomes, scheduling, and reporting. Inspect relevant installed skills and CLI tools as well as connected harness tools. Use targeted discovery within authorized locations; environment key names or an MCP inventory alone do not establish available capabilities or working access.

Read applicable help and verify essential access with a minimal authorized read-only check. Distinguish installed, configured, verified, and unavailable tools. Resolve the scheduler through [scheduling.md](scheduling.md). Before building helpers or integrations, check for existing ways to do the work.

Always review the proposed tools and workflows with the owner once, even when discovery appears complete. Show what was found, what was verified, and remaining gaps; ask whether an existing tool or workflow was overlooked. Reuse tools and answers already supplied instead of making the owner rediscover them for you.

## Resolve the operating agreement

Ask one consequential question at a time, explain the trade-off, and recommend an answer when helpful. Resolve facts through inspection and decisions with the owner. Cover the following areas, reusing established answers and recording choices as they arrive:

- Product, broad responsibility, ongoing or bounded scope, worthwhile progress, and stopping conditions. Leave concrete future objectives to the agent within that scope.
- Evidence sources, access, measurement definitions, observation windows, and checks for implementation and outcomes. Resolve essential gaps; record accepted adequate fallbacks and deferred capabilities with their effect on scope.
- Standing permission for applicable changes, publication, deployment, rollback, and communication, including reserved owner decisions.
- Related work, the product boundary for shared history, discovery of actual changes, and coordination of interference.
- Initial assignment and timing, timezone, continuation policy, routine reporting cadence and authorized destination. Establish the owner request, reply, and explicit resumption procedure in [owner-input.md](owner-input.md).
- File locations and the artifact policy in [workspace.md](workspace.md), including Git tracking, commit/push authority, and durable storage outside Git.
- Optional autonomous-run limits and project-specific cost instructions: supplied usage sources, units, periods, shared scope, and pending consumption. Settle these before activation; do not make them a prerequisite to ordinary setup investigation unless the owner's instructions also cover setup. No fixed provider or numerical limit is required.

## Prepare, confirm, and activate

Prepare the brief, current handoff, and initial task definition. Validate and preview configuration without enabling future runs. If a tool's registration can start work, defer registration to activation. Empty fields, publication permission, and a proposed schedule do not establish readiness.

Before declaring setup ready, check that each applicable area above is resolved, essential capabilities are verified, and remaining gaps have adequate owner-accepted fallbacks. An essential unresolved prerequisite keeps the responsibility in draft; it does not prevent useful authorized preparation.

Show one concrete summary: responsibility and first assignment; tools, verification and accepted fallbacks; authority and autonomous-run limits; schedule and timezone; reports and owner-input procedure; artifact policy. Link the prepared files. Then ask one final explicit confirmation: **“Activate this responsibility with these settings?”** Even previously granted action permissions do not replace this confirmation of the assembled setup. An empty answer or elapsed time is not consent. If the owner changes settings, update the summary before requesting confirmation of the revised setup.

After affirmative confirmation, record it with the agreed brief, activate the task using the selected scheduler, and inspect its actual enabled state and next run. Retain the task identity and receipt. Report activation only when verified; keep failed or uncertain activation visible and inspect existing state before retrying. Carry standing authority into ordinary later runs without repeated approval.
