# Design interview

## User intent

Build a general approach to complicated work that spans multiple days, potentially continues for months, and uses past attempts to choose future work. Impulse already schedules future agent assignments. The user prefers a SKILL.md with evaluations, while explicitly asking for research and throwaway prototyping before settling the solution.

The agent should retain what it tried, what worked or did not, what it learned, and how its assumptions changed. It should be able to continue improving, or stop when the remaining opportunity is sufficiently small. Relevant examples: page/content experiments, feature feedback and rollout, and monitoring errors after commits or deployments.

## Accepted decisions

1. **Standing authorization within each goal's agreed limits.** Accepted September 8, 2026. The owner authorizes pursuit of a goal at setup, including running experiments and adopting winners within that scope. Routine actions inside those limits do not require repeated approvals. See [ADR 0001](adr/0001-standing-goal-authorization.md). Specific limits and how changes to authorization propagate remain to be designed. This decision concerns the future system; no current website rollout was requested.
2. **Each goal owns its continuity through a durable workspace.** Accepted September 8, 2026. Saved attempts, evidence, learnings, and pending work must be sufficient for a completely fresh agent to continue independently of the original conversation or agent. See [ADR 0002](adr/0002-goal-workspace-owns-continuity.md). This does not require changing models between runs. Decisions 8 and 17 subsequently establish product-scoped sharing and readable files.
3. **The agent may choose objectives and close completed or impossible work.** Accepted and clarified September 8, 2026. A bounded assignment can terminate when its requested outcome is reached or impossible within its constraints. An ongoing responsibility continues across individual objectives while useful work remains within scope. See [ADR 0003](adr/0003-agent-selects-objectives-and-can-terminate.md). Do not require approval for each ordinary objective selection or justified termination. Resolvable blockers use the accepted pause/manual-resume policy.
4. **Prototype across diverse use cases.** Explicit user requirement, September 8, 2026: include A/B testing pages to maximize revenue and weekly product improvement from analytics, along with the previously requested feedback and bug-monitoring cases. A single page-variant demonstration is insufficient. Cover continuity, changed evidence, autonomous prioritization, reached objectives, and impossible objectives in this exploration.
5. **Recall over many months is a core prototype requirement.** Explicit user emphasis, September 8, 2026. Fresh agents must retrieve relevant prior actions and use their outcomes and reasoning during tasks that accumulate months of history. Preserving files alone is insufficient. See the [recall evaluation design](recall-evaluation.md), which covers diverse domains, growing archives, changed names/conditions, corrections, and agent-authored history. Four initial probes using synthetic year-long archives are complete; they do not yet establish reliability.
6. **Test patterns from the existing indexing and Biomogging report tasks.** Explicit user request, September 8, 2026. Use their current-state ledger, recovery context, attempt reservations, weekly action/evidence records, follow-up rules, and publication receipts as grounded comparison candidates. See [pattern transfer](research/pattern-transfer.md). Exercise synthetic equivalents; this request does not require changing the existing live tasks.
7. **Retain action records and decision evidence until explicit deletion.** Accepted and extended September 8, 2026. Compact summaries support routine work while underlying action records and supporting evidence remain searchable for later recovery and checking. The user explicitly confirmed keeping history after termination so future responsibilities on the same project can consult it, until the owner deletes it. See [ADR 0004](adr/0004-retain-actions-and-decision-evidence.md). Decision 17 subsequently selects readable files; exact file formats and index design remain open.
8. **Scope shared history and learnings to each product in v1.** Accepted and clarified September 8, 2026. Each responsibility keeps its own history; other responsibilities for the same product can consult it, with shared findings linked to original evidence and applicable conditions. The user accepted deferring cross-product learning to a later version. See [ADR 0005](adr/0005-share-history-within-a-product.md). The retrieval mechanism remains open.
9. **Coordinate overlapping work according to impact.** Accepted and clarified September 8, 2026. The user wants experiments, fixes, and feature development to coexist as they would in a software company. The earlier recommendation that ordinary changes generally wait for an experiment was too restrictive and is not accepted. Compatible work can proceed concurrently; actual interference needs coordination and appropriate adjustments to affected evaluations. See [ADR 0006](adr/0006-coordinate-overlapping-work-by-impact.md).
10. **Version one runs on one machine.** Explicitly confirmed September 8, 2026. Use the existing Impulse installation with multiple coordinated responsibilities on that machine. Distributed execution and coordination across machines are outside v1. See [ADR 0007](adr/0007-scope-v1-to-one-machine.md).
11. **Deliver v1 as a skill bundle on Impulse.** Accepted September 8, 2026. Include SKILL.md, templates, evaluations, and small local helper commands where prototype evidence justifies them. Impulse continues to own scheduling; exact helpers and production language are not yet selected. Decision 17 subsequently selects readable files for storage. See [ADR 0008](adr/0008-deliver-a-skill-bundle-on-impulse.md).
12. **Pause, notify, and require explicit owner resumption for resolvable blockers.** Accepted and clarified September 8, 2026. Preserve the task's context and identify the missing prerequisite. The owner fixes the blocker and resumes the task. The user explicitly rejected automatic restoration checks as unnecessary complexity; no polling or automatic restart is added for a paused task. Normal scheduled waits for observation windows, cooldowns, and expected temporary conditions remain separate. Impossible termination requires evidence of no viable route within the agreed constraints. See [ADR 0009](adr/0009-pause-for-resolvable-blockers.md).
13. **Review changes to the shared skill; adapt task plans and learnings autonomously.** Accepted September 8, 2026. Agents may update their plans and evidence-backed learnings within standing authorization. Proposed changes to the shared SKILL.md need evaluations and owner review before adoption. A useful lesson from one responsibility does not itself authorize changing the common workflow for all responsibilities. See [ADR 0010](adr/0010-review-changes-to-the-shared-skill.md). The first-pass skill and evaluation artifacts remain frozen records of what was tested.
14. **Responsibility limits are optional and can constrain domain work.** Accepted and clarified September 8, 2026. The user explicitly endorsed optional limits and supplied “only A/B test five articles at a time.” This counts articles with active experiments, including observation periods between runs; it is distinct from a limit on running agents or the lifetime number of experiments. The user places responsibility for respecting task-specific paid-service budgets with the working agent, using available usage information, rather than requiring Impulse to become a budget controller. Harness subscription allowances and paid APIs such as Firecrawl are relevant examples. See [ADR 0011](adr/0011-allow-optional-responsibility-limits.md). No particular spending allowance or metering implementation is selected.
15. **Cost instructions are supplied per project and can use custom sources.** Clarified September 8, 2026. The user supplies the project's cost restrictions and how usage information is obtained; actual tasks may use any number of different methods. `ccusage` and Firecrawl MCP are examples, not required integrations. A shared project allowance must retain its scope across responsibilities. See the updated [ADR 0011](adr/0011-allow-optional-responsibility-limits.md).
16. **Build thorough task setup into the skill.** Accepted and clarified September 8, 2026. The user wants to be grilled about the details of a long-horizon responsibility because the agent will act autonomously over a long period. This strengthens the earlier recommendation of a focused minimal intake: cover the task's consequential details thoroughly, one question at a time, preserving already-supplied answers. A separate `grill-me` invocation is optional. See [ADR 0012](adr/0012-build-thorough-setup-into-the-skill.md) and [setup-interview guidance](setup-interview.md).
17. **Use readable local files with any index rebuildable from the records.** Accepted September 8, 2026. The user agrees that modern LLM harnesses work well with files and does not want a vector database for v1. Original records retain the knowledge and evidence; an index helps locate them and can be regenerated without losing unique knowledge. Exact formats and whether an index or helper improves recall remain prototype questions. See [ADR 0013](adr/0013-use-readable-files-for-durable-history.md).
18. **Agree reporting at setup and notify on consequential transitions.** Accepted September 8, 2026. Establish a routine report cadence and destination during setup, with immediate notices when a task pauses, terminates, or needs an owner decision. Other runs update the durable history. A weekly digest is an example, not a fixed default. See [ADR 0014](adr/0014-agree-reporting-at-setup.md). No destination or external messaging integration has been selected for this project.

## Scope clarification

The user reiterated that this must cover responding to feedback, monitoring for bugs after PRs, and improving a product from weekly metrics. These were part of the original scope. A universal requirement for one fixed success measure or a final completed state would be too narrow; the previous question about fixing the success measure was not accepted.

The design must accommodate ongoing responsibilities as well as finite outcomes. For feedback work, evidence can include reproduced friction and whether a delivered change addresses it. For monitoring, an uneventful observation window may be valid work and still leave future monitoring active. For product improvement, the agent may need to identify which problem is worth pursuing before choosing an intervention or its evaluation method. A merged PR is a discovery signal; deployment and relevant exposure need verification before evaluating production outcomes.

Standing authorization and durable continuity remain accepted. The user's agreement establishes a broad responsibility with agent-selected objectives; CONTEXT.md now uses those terms in place of the earlier overloaded goal wording. An ongoing responsibility continues after individual improvements while useful work remains. The existing ADRs do not require a numeric KPI or a finish date.

## Current exploration

The owner authorized building the complete candidate and running full simulated cycles with “work on that.” The [candidate](../skills/long-horizon/SKILL.md), [evaluation implementation](../prototypes/full-cycle/README.md), and [findings](../prototypes/full-cycle/NOTES.md) now exist. The main comparison completed 48 fresh sessions across four domains with independent service effects and agent-maintained records. Baseline and skill both recovered interruptions and later corrections; broad retrieval and directory-boundary issues limit the conclusion, and the skill used more recorded work in this sample. Local packaging preserves the exact evaluated candidate. No shared skill installation or real-product pilot has occurred.

The lifecycle, v1 history-sharing boundary, readable-file storage approach, and owner reporting policy are resolved. A disposable skill candidate and [four independent fresh-agent recall probes](../prototypes/agent-recall/NOTES.md) are complete. A subsequent [dense-history comparison](../prototypes/recall-comparison/NOTES.md) tested the no-skill baseline, frozen skill, and a narrow retrieval revision on matching 4,804-record archives. All three recovered a later correction from a terminated responsibility and made supported decisions. The revised arm used bounded content searches, but all arms initially enumerated filenames too broadly; regular fixture structure still made critical records easier to isolate.

[Four agent-maintained handoff chains](../prototypes/agent-handoffs/NOTES.md) then completed three fresh sessions each. Agents chose their own records and retained original evidence and corrections; all four final decisions were supported in manual review. The reviewer verified all eight memory handoffs without editing their contents. Final memories reached 27–35 KB, and all final agents reported reading the full small archive. This partially exercises agent-authored continuity, but not long accumulated sequences, selective recall beyond context capacity, or actual interventions. Next work should test longer histories with competing corrections, missing/stale indexes, and full cycles against controlled services. This is behavioral prototyping, not production implementation or acceptance. File formats, helpers, and evaluation thresholds remain to be decided from evidence. Skill-creator guidance provides the independent forward-testing method.

The user also supplied [Ponytail](https://github.com/DietrichGebert/ponytail) as a reference for skill-repository structure and prompt evaluations. The [completed source review](research/ponytail-evaluation-patterns.md) records useful methods and limitations at a pinned revision; its benchmark scores were not reproduced. A [repository/evaluation layout proposal](repository-layout.md) captures the transferable separation of runtime skill, deterministic checks, behavioral evaluations, and preserved results. Baseline isolation, grader calibration, treatment/fixture provenance, and completion-sensitive scoring have been added to the evaluation plan; no evaluation framework or production repository migration has been selected.

## Exploration assumptions, not accepted decisions

- Working directory/name: `long-horizon`.
- Use Python for a disposable terminal prototype, following the existing indexing and report helpers. This does not select a production runtime.
- Test continuity with short-lived sessions and explicit saved state. Compare alternatives before choosing an architecture.
- Keep task-specific interpretation of evidence separate from generic continuity. An experiment's significance, an indexing acknowledgment, and a reduction in observed errors mean different things.
- Candidate general loop: inspect current signals and history, choose useful work (or wait), act within scope, verify the relevant outcome, update the accumulated understanding, and arrange the next observation. Not every cycle changes the product, and not every ongoing responsibility terminates.
- Coordination candidates to prototype: discover ongoing work, make intended changes visible, assess interactions, record the actual changed/deployed revisions, and recheck compatibility after waking. Include human or unrelated-tool changes that bypass these records. These are candidate mechanics for the accepted coordination requirement, not a mandated shared registry or distributed lock design.

## Setup flow

The owner selected a thorough built-in interview. Follow the one-question-at-a-time approach of the installed [grilling skill](../../../.agents/skills/grilling/SKILL.md), which [grill-me](../../../.agents/skills/grill-me/SKILL.md) delegates to. The new skill should be usable on its own and should reuse any prior interview's decisions. The accepted depth, project-specific cost handling, and candidate setup probes are captured in [setup-interview guidance](setup-interview.md). The complete candidate's sparse-setup probe asked which product to improve and did not invent authority or activate work. It tested the initial turn only; a full interactive setup conversation remains untested.

## Candidate language to resolve in the interview

- **Effort**: the enduring pursuit of an outcome across scheduled runs. Distinct from Impulse's registered task and individual run.
- **Attempt**: an intervention or investigation with an identity, a rationale, and an assessable outcome.
- **Observation**: evidence collected at a particular time about a particular subject and conditions.
- **Learning**: a revisable conclusion supported by observations; retains where and when it applies.
- **Wake condition**: what should cause another run, such as a date, available evidence, or an external event.

These are proposals. Agreed terms live in [CONTEXT.md](../CONTEXT.md); create ADRs only for accepted decisions with meaningful trade-offs.
