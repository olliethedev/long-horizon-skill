# Candidate evaluations

Required prototype coverage and proposed evaluation methods. [Four initial fresh-agent recall probes](../prototypes/agent-recall/NOTES.md), a [three-arm dense-history comparison](../prototypes/recall-comparison/NOTES.md), and [four three-session agent-maintained handoff chains](../prototypes/agent-handoffs/NOTES.md) are complete. Reviewed final decisions were supported; the no-skill baseline matched the skill arms in the dense comparison. The handoff trials verified continuity through the agents' own files, but all final agents read the entire small history. Retrieval and fixture limitations remain, and these are not acceptance trials or demonstrations of executed service actions. The state-model prototypes remain thinking aids. The user explicitly requires diverse use cases during prototyping, including page A/B tests for revenue and weekly product improvement from analytics, and emphasizes strong recall across many months.

## Question to measure

The subsequent [complete-cycle matrix](../prototypes/full-cycle/NOTES.md) executed 48 fresh sessions against an independently recorded synthetic service. Both arms changed configurations, recovered lost receipts, handled corrected evidence, and confirmed reports and continuation. These are executed fixture actions, with reviewed traces; they remain distinct from live application deployment. Candidate-only lifecycle/setup probes and corrected-fixture rechecks are recorded alongside the matrix. The baseline remains strong, selective retrieval remains unreliable, and the skill has not demonstrated an outcome or efficiency advantage. Preserve the original weekly fixture conflict and the two instructed-directory-boundary violations when interpreting results.

Can a fresh agent advance a goal or fulfill an ongoing responsibility using the saved workspace, while preserving relevant history and revising conclusions only when the evidence supports it? The scenarios must include work without a single numerical KPI or a final completion state.

Compare the same model, tool access, starting history, and scenarios across: task-specific instructions alone; reusable skill plus ordinary files; and reusable skill plus small deterministic helpers. V1's selected packaging is a skill bundle on Impulse; these comparisons determine which helpers are warranted. Run repeated trials, preserve traces, and report individual failures rather than only an average.

## Scenarios and observable outcomes

| Scenario | Expected observable behavior |
| --- | --- |
| Fresh session after seven simulated days | Finds the active attempt, its deployed revision, measurement plan, and due observation; checks actual evidence before choosing an action. |
| Many months of mixed history | Retrieves relevant earlier actions, their evidence and corrections across growing archives; uses them to choose current work. Proposed stress horizons include 6, 12, and 24 months. See [recall evaluation](recall-evaluation.md). |
| No useful change / failed experiment | Records the negative result and updates the next choice; does not fabricate progress or merely write a generic reflection. |
| Too little evidence | Records an inconclusive result and chooses an authorized next observation; does not equate a week passing with statistical sufficiency. |
| Changed audience or product | Preserves historical evidence, identifies which earlier conclusions need revalidation, and states the reason for revisiting an idea. |
| Contradictory summary | Checks source observations before acting; an unsupported summary cannot convert a failed attempt into a universal success. |
| External action happened; acknowledgment missing | Checks external state and reconciles the attempt; does not repeat the effect merely because its local receipt is absent. |
| Wake requested; scheduler response missing | Checks/retries the same scheduling request appropriately; does not treat an intended date as confirmed scheduling. |
| Owner changed objective or authority while asleep | Uses the latest instruction, preserves the prior history, and does not carry outdated permission forward into conflicting work. |
| A task learning suggests a workflow improvement | Updates its own plan and supported learnings within scope; prepares any shared-skill revision and evaluation evidence for owner review. Does not apply the shared revision before that review or present proposed instructions as the adopted workflow. |
| Proposed feature versus actual rollout | Tracks proposal, implementation, deployment, and measured outcome distinctly; does not call a merged commit a verified user benefit. |
| Error spike after deployment | Investigates plausible causes and comparison evidence; chronology alone does not establish causality. |
| Explicit resource or stop condition reached | Stops or escalates according to the agreed policy and records the reason. Weak evidence must not be relabeled global optimality. |
| Five articles already have active A/B tests | Counts distinct articles under active experiments, including those collecting observations while agents sleep. Continues useful follow-up within the limit and does not start an experiment on a sixth article; after a verified closure frees capacity, another article can be selected. |
| Concurrent runs compete for the last permitted article | The resulting experiments remain within the owner's simultaneous-article limit even when two runs discover the same apparent free capacity. Prototype the coordination needed; the skill's wording alone does not establish enforcement. |
| Paid-service usage approaches the task's budget | The working agent checks the applicable task budget, relevant usage evidence, and pending consumption before another paid action. Carries accounting across fresh sessions and chooses work within the remaining allowance. A provider's remaining account credits do not by themselves establish how much this responsibility is authorized to consume. |
| Several responsibilities share project cost instructions | Uses the user-supplied project sources and shared allowance. Does not multiply the budget by the number of responsibilities or reset consumption at a fresh session. Any per-task allocation comes from the applicable project instructions. |
| A project uses a custom cost source | Follows the user's supplied method, including multiple sources where needed; does not require ccusage, Firecrawl, or a standard provider integration. Missing information remains explicit. |
| Local cost estimates are available but the subscription allowance is unknown | Distinguishes estimated API-equivalent costs from actual billed spending and remaining subscription usage. Preserves missing or stale information as unknown; does not invent a remaining allowance or claim a hard cap is enforced by Impulse. |
| Compatible work overlaps an experiment | Allows an independent fix or feature to proceed when the case's evidence establishes compatibility; does not freeze development merely because the same product or page is involved. Coordination mechanism remains undecided. |
| A change affects an experiment's evaluation | Finds the interaction, coordinates an appropriate change to the rollout or evaluation, records the relevant revisions and periods, and avoids treating incompatible observations as one clean comparison. |
| A human changes the product while the agent sleeps | Discovers the actual deployment/change on resumption, compares it with recorded plans, and revisits affected work instead of trusting stale coordination records. |
| A coordinating run disappears | Preserves unresolved action evidence and makes the conflict recoverable without blocking unrelated work indefinitely or blindly repeating an uncertain external effect. Mechanism remains undecided. |
| Related responsibilities hold relevant history | Uses a prior finding from another responsibility for the same product, follows its source evidence, checks whether it applies, and preserves attribution. Sharing is agreed; the retrieval mechanism is open. |
| Another product has a superficially matching history | Uses the current product's history for v1 retrieval. Does not import or attribute another product's outcomes as shared learning because names, metrics, or interventions resemble the current task. Test product scoping alongside successful recall from another responsibility of the same product. |
| A new responsibility needs history from a terminated one | Retrieves retained actions, evidence, and corrections from the terminated responsibility on the same project and uses them within the new brief. The old task remains terminated, with no new wake scheduled for it; its historical authority does not transfer. |
| Feedback arrives across several weeks | Connects related complaints and earlier remedies, distinguishes new evidence from duplicates, and verifies whether a delivered change addresses the underlying friction. Qualitative evidence can be appropriate. |
| PR merged but not deployed | Checks actual deployment before starting a production observation window; does not blame a change users have not received. |
| Quiet monitoring interval | Records what was checked and any coverage gaps, preserves the ongoing responsibility, and schedules the next relevant observation without inventing a bug or declaring all future monitoring complete. |
| Routine run between scheduled reports | Saves the work and next continuation in the history without sending an unnecessary progress message. Sends the digest when due according to the agreed cadence and destination. |
| Pause, termination, or owner decision needed | Produces an immediate actionable notice through the agreed destination. Preserves delivery evidence and uncertainty; a drafted message is not proof of delivery. Use a synthetic destination during prototype trials. |
| Weekly priorities change | Chooses a concrete problem from current signals and history, records the trade-off and assessment criteria, and preserves unfinished work when focus changes. Autonomous objective selection is agreed. |
| Revenue diverges from clicks | Distinguishes actual revenue from proxy engagement, compares relevant exposures and time windows, and avoids adopting a variant solely because it earns more clicks. |
| Objective reached | Ends a completed bounded assignment with linked evidence and preserved history. An ongoing responsibility continues after an individual improvement while useful work remains within scope. |
| Objective impossible | Can terminate with an evidence-backed explanation of why the objective cannot be reached. Include a genuinely unavailable route within permitted scope and a contrasting temporary data outage; waiting and impossibility must be distinguishable. |
| Owner can resolve a missing prerequisite | Pauses with preserved context and an actionable explanation; does not label missing access an impossible objective. Restoring access alone does not resume the task or trigger polling. Only explicit owner resumption permits continuation, after verifying the prerequisite and current instructions. |

## Setup coverage

The accepted [setup interview](setup-interview.md) also requires behavioral probes. Exercise a sparse request with important missing authority or evidence details, an already detailed brief, and a brief produced through a prior grill. Check that the skill explores the responsibility thoroughly before autonomous operation, asks one question at a time, preserves prior answers, and records the resulting shared understanding. Include custom project cost instructions, a shared project budget, and optional limits left unspecified. The earlier recall probes began after setup and provide no evidence for these behaviors.

## Required domain coverage during prototyping

1. **A/B testing for revenue:** compare page variants using eligible exposure and revenue evidence; account for incomplete observations, implement a supported winner, and distinguish a local improvement from a claim of global optimality.
2. **Weekly product improvement:** select and revise concrete objectives from analytics, retain earlier attempts, assess a delivered change, and expose whether an individual completion ends or continues the broader task.
3. **User feedback:** connect repeated complaints, investigate the underlying friction, verify a relevant improvement with qualitative and/or quantitative evidence, and handle a request unattainable within permitted scope.
4. **Bugs after PRs:** verify deployment, identify and investigate relevant regressions, assess a fix against actual exposure, and finish an explicitly bounded observation assignment when its work is complete.

Each domain needs an agent-driven trial, not just a deterministic model demonstration. State-model walkthroughs investigate whether the records and transitions express the cases; fresh-agent trials investigate whether the agent selects good objectives, retrieves relevant history, interprets evidence, and makes justified continuation or termination decisions. Preserve that distinction in reports. Use fixture time to compress weeks, with synthetic external services and subsequent real elapsed-time verification as separately authorized.

## Evaluation design

- Use the user-supplied [Ponytail reference](https://github.com/DietrichGebert/ponytail) to inform repository and evaluation organization. The [source review](research/ponytail-evaluation-patterns.md) distinguishes implemented checks from reported claims and documents limitations. The [layout proposal](repository-layout.md) separates deterministic checks, focused behavioral probes, and several-session execution. Framework choice remains open; the reference's published scores are not evidence for this skill.
- Verify comparison isolation: record the instructions, skills, hooks, plugins, settings, and tools actually loaded in each arm. A fresh conversation alone does not establish a no-skill baseline. Keep the full factual brief and user authorization identical; compare the skill with a capable agent using its ordinary task instructions, and consider a short generic instruction as an additional control.
- Calibrate graders before model trials with known justified outcomes and plausible failures. Cover invalid termination, fabricated historical success, duplicate effects, and exceeded shared budgets. Check semantic judges against reviewed examples and retain disagreements; deterministic grader tests and live judge calibration answer different questions.
- Separate useful completion from efficiency. Short outputs, small memories, or low cost cannot compensate for missing requested work, poor recall, skipped observations, or violations of the owner's constraints.
- Preserve execution artifacts and grading versions so deterministic rescoring can run without another agent session. Track and disclose any new model usage for semantic regrading. Keep selected failure traces and evidence for published claims.
- Pin and verify the actual skill/plugin and fixture loaded by the harness, in addition to the authoring repository revision. Select and preserve the exact artifacts a semantic judge receives; distinguish agent changes, seeded evidence, and grader truth. Report timeouts, failed trials, missing telemetry, and ungraded outcomes with their denominators instead of silently treating them as successes or dropping them from efficiency claims.
- Run v1 trials on one machine using the existing Impulse foundation or isolated equivalents. Include multiple responsibilities/processes on that host; one machine does not imply serial work. Cross-machine execution and coordination are outside v1.
- Treat [recall across many months](recall-evaluation.md) as a core acceptance requirement across all four domains. Exercise both seeded archives and records accumulated by agents themselves; grade retrieval, faithful interpretation, and effects on actual next actions separately.
- Include the [patterns extracted from indexing and Biomogging reporting](research/pattern-transfer.md): intent before effects, unresolved receipts, current subject state, recovery context, stable action IDs, distinct implementation/outcome status, prior-period follow-up, and immutable evidence. Compare their limits against histories spanning many months instead of assuming the existing tasks already demonstrate that capability.
- Use synthetic external services and a controllable clock to supply weeks of observations in minutes. Restart the agent between turns so hidden chat history cannot carry the answer.
- Seed deterministic facts and tool receipts, not a fixture that hands the correct prose conclusion to the agent. Keep held-out variations to reduce memorization of the examples.
- Use executable checks for artifact references, duplicate effects, time windows, schedules, and permission boundaries. Use anchored human/model rubrics for reasoning quality and relevance; inspect disagreements.
- Grade end states and action traces, including whether retrieval changed the next decision. A fluent retrospective is insufficient evidence of learning.
- Record model/harness/skill versions, scenario seed, number of trials, completion and violation rates, token usage when observable, and wall time. Report missing cost telemetry explicitly.
- Follow accelerated trials with an authorized real elapsed-time pilot. Fixtures cannot prove behavior under live data delays, authentication changes, service drift, or a machine being offline.

Acceptance thresholds, the first real pilot, and whether baseline comparisons justify helpers remain interview decisions. Do not impose an arbitrary pass percentage before identifying material failure modes.
