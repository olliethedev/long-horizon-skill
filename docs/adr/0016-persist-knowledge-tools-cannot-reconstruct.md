# Persist knowledge that tools cannot readily reconstruct

The first real product run did useful work but generated substantial operational records and repeated recovery archives. Moving those artifacts out of Git had not reduced their production. The owner requested a simpler core that gives the harness discretion over working methods.

Retain the onboarding agreement, useful discoveries, failed or inconclusive approaches, and enough pending context to continue unfinished work. Query source systems for information they can reproduce. Use existing revision/recovery facilities, keeping additional material when the task needs it. A pending experiment can become its learning note; no record schema, per-run narrative, raw-export archive or backup procedure is mandatory.

This revises the retention scope in ADRs 0004 and 0013, while preserving native file search, useful knowledge after termination, standing authority, coordination and scheduler continuation. It does not retroactively erase earlier project evidence. Existing project-specific procedures should be simplified when the owner authorizes their migration.

Validate the new core with one matched task and five fresh Codex sessions per arm, including onboarding. Use the same short request, tools and owner facts in both arms; allow the baseline to ask its own questions. Judge outcomes, continuity and effort rather than compliance with a preferred structure. Preserve the historical studies as evidence of earlier versions.
