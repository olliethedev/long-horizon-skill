# Setup interview design and review cases

The installed [setup procedure](../skills/long-horizon/references/setup.md) is the authoritative workflow. [ADR 0012](adr/0012-build-thorough-setup-into-the-skill.md) records why the interview is built in. The refinement follows an owner-reviewed setup that required manual prompts to discover an existing CLI and settle artifact persistence after the agent had called onboarding complete.

The revised completion boundary is a verified, owner-reviewed toolset and concrete operating agreement, followed by one explicit confirmation of the assembled setup before activation. Setup investigation may precede autonomous-run limits. Existing responsibilities retain standing authority.

## Focused review cases

Use synthetic projects and inspect discovery, questions, saved state and attempted scheduler operations. These are reusable review scenarios, not generated model outputs or scores.

| Case | Expected behavior |
| --- | --- |
| A short organic-growth request; analytics CLI and publishing skill already installed, no analytics MCP | Inspect relevant installed tools and project configuration, verify essential access, review the proposed workflow with the owner, and ask about omissions before inventing integrations. |
| Revenue experiments lack exposure measurement; ordinary content improvement has adequate search data | Keep experiments unready until measurement works, or obtain acceptance of the narrower content scope. A future optional capability does not block useful independent work. |
| Weekly product improvement has deployment permission but no artifact or reply policy | Resolve those gaps; deployment permission alone does not complete onboarding. Prepare and validate files, show the full summary, and await final activation confirmation. |
| A prior interview supplies tools, timing, shared custom cost instructions and Git policy | Reuse supplied decisions, review the assembled toolset, and ask only unresolved questions plus final activation confirmation. Do not force a numeric KPI or budget for projects without one. |
| The owner changes the proposed first-run time, or does not answer confirmation | Update and validate the revised setup before confirmation. Do not activate on silence, a stale summary, or elapsed time. Verify actual scheduler state after authorization. |
| An active release monitor needs owner access; independent log analysis remains useful | Save one actionable request, deliver through the agreed channel, hold dependent work, and continue independent work. If all useful work is blocked, disable future runs. A one-way notification cannot receive an answer; explicit resume and prerequisite verification are required. |
| Four responsibilities retain months of exports with renamed subjects and later corrections | Start from concise handoffs, follow relevant source identities and corrections, and link shared evidence. Keep originals, avoid copying them into every report, and verify storage access/backups when evidence is outside Git. |
| An established feedback responsibility has a fuller Git policy when the skill updates | Preserve its current owner instructions and standing authority; do not re-onboard or silently replace its artifact policy. An explicit owner-requested migration may change it while retaining evidence and references. |

The onboarding revision received a local scenario walkthrough and consistency review, plus the repository's deterministic checks. No additional native-model sessions were launched. These checks establish instruction coverage and bundle integrity, not that a harness will reliably perform the workflow. Earlier scheduler-choice probes used captured inventories and supplied owner answers; they did not test real discovery or an adaptive interview. Historical workflow comparisons retain their original skill bytes and results.
